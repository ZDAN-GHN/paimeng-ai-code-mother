# 文档组织规则

`docs/` 只保存当前有效的契约、参考和架构决策。过程记录、一次性调查和已经完成的计划不留在顶层；它们的生命周期见下文。

## 目录职责

| 位置 | 放什么 | 不放什么 |
| --- | --- | --- |
| `docs/*.md` | 当前有效的实现契约、接口、运行约束和专题参考，例如 `implementation-contract.md`、`migration-contracts.md`、`model-routing.md`、`artifacts.md`。 | 未完成的想法、任务日志、完成后的计划。 |
| `docs/plans/` | **仍然在推进的计划**。每份计划写清目标、范围、当前状态、验收标准和未完成边界。 | 已完成、已放弃或被替代的计划。 |
| `docs/plans/archive/` | 已完成、已放弃或被替代的计划。作为历史记录保存，不按当前代码重写。 | 当前运行约定、现行命令的唯一来源。 |
| `docs/adr/` | 已接受的持久架构决策。编号递增，正文直接写决定、背景和真实取舍；只记录难以回退、没有上下文会显得意外、且存在真实替代方案的决定。 | 每个小改动、实现步骤、临时选择。 |
| `docs/migrations/` | 一次性迁移的设计、数据和演练记录。 | 当前接口契约。 |

领域术语以仓库根的 [GLOSSARY.md](../../GLOSSARY.md) 为准。

脚本目录只保留可复用入口；一次性脚本的创建、执行和删除规则见 [scripts/README.md](../scripts/README.md)。

## 计划生命周期

1. **开始**：在 `docs/plans/` 新建计划，文件名用简短的 kebab-case；写目标和范围，不写“以后可能”。
2. **推进**：计划是活文档；状态、验收结果和未证明边界跟着变化更新。命令、表结构和测试清单优先链接到代码，不复制成第二份事实。
3. **完成或被替代**：先判断是否有需要长期保留的架构决策。符合 ADR 标准的，提取到 `docs/adr/`；不符合的，让计划归档即可。
4. **归档**：把计划移动到 `docs/plans/archive/<name>.md`，在文件标题下加归档日期、当前入口和相关 ADR 链接；在 `docs/plans/archive/README.md` 增加索引；更新所有指向旧路径的引用。
5. **归档后**：保留当时的结论、命令和证据链接，不回写成“现在仍然如此”。需要说明当前行为时，链接当前文档或写新的 ADR。

**`docs/plans/` 中出现完成计划即视为文档错误**，不是“先放一放”。

## ADR 的边界

只有同时满足以下条件才建 ADR：

- 以后改变它的成本明显；
- 新读者看代码会问“为什么这样做”；
- 当时存在真实替代方案，并且有具体理由选择了现在这条。

一份计划通常只需要 0–3 个 ADR。计划里的实施顺序、命令、表名和测试数量不属于 ADR；它们留在归档计划或代码中。

## 命名与链接

- 文件名使用小写 kebab-case，不加日期；计划名描述任务，不描述“最终版”“新版”。
- 文档之间使用相对链接；移动文件时同步更新 `README.md`、归档索引和代码注释中的链接。
- 已应用的数据库迁移是不可变历史；迁移文件内的注释可以继续指向旧计划名，不要为了改注释而改变校验和。
- 当前行为以代码、测试和顶层契约为准；归档计划只解释当时为什么这样做。
